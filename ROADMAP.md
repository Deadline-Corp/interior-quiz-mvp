# Deadline Interior Planner — описание проекта и roadmap

*Версия 0.1 · 2026-06-11 · живой документ — правим по мере решений*

## 1. Видение

Веб-сервис, в котором покупатель квартиры/кондо/виллы на Пхукете за один сеанс **проектирует своё жильё и покупает всё наполнение**: рисует (или выбирает из шаблонов) план юнита → расставляет мебель и технику из живых каталогов нескольких крупных магазинов с проверкой «влезает / не влезает» → видит актуальную цену → оплачивает → магазины собирают и доставляют каждый свою часть.

Почему это сработает (из deep research 2026-06-10, отчёты в Obsidian Vault → `Business/Analysis/*/2026-06-10 Apartment_planner_marketplace/`):
- Полных аналогов нет ни глобально, ни в Таиланде, ни в РФ
- Пхукет: 10 400+ новых кондо в 2024 (+148%), русские = 25% покупателей кондо / ~50% вилл
- Конкуренты-комплектовщики работают офлайн «позвоните нам», без конфигуратора и прозрачных цен
- NocNoc (тайский home-маркетплейс) закрылся в фев 2026 — ниша свободна, привычка покупать онлайн осталась

Рынки по очереди: **Пхукет → Россия → Казахстан → мир.**

## 3. Фаза 1 — конечная точка (спека)

Пользовательский путь, который должен работать end-to-end:

1. **Регистрация/вход** — email + Google OAuth (гость может проектировать, аккаунт нужен для сохранения и заказа — см. «Допущения»)
2. **План юнита** — выбор из шаблонов типовых планировок (кондо-проекты Пхукета) или свой план: комнаты, размеры, формы
3. **Каталог** — фильтры по типу (кухня, диван, кресло, свет, техника…), магазину, цене; данные из каталогов крупнейших тайских ритейлеров и производителей
4. **Конструктор — два связанных вида** (уточнённое видение, 2026-06-11):
   - **План сверху (plan view)** — расстановка по габаритам, проверка «влезает / не влезает», коллизии. Отвечает на вопрос «поместится ли».
   - **Вид на стену (elevation / фронтальный вид)** — клиент выбрал помещение → видит одну стену в лоб, как будто стоит к ней лицом → drag-and-drop ставит товары их **реальными изображениями** в **выбранном цвете/варианте** (красные фасады → красные на картинке; зелёный холодильник → зелёный). На выходе — фотореалистичная картинка будущей комнаты с настоящими товарами. Отвечает на вопрос «как это будет выглядеть дома».
   - Оба вида делят одну модель данных (товар = габариты + позиция + выбранный вариант); plan view держит логику размеров, elevation — визуализацию. Партнёрский `index.html` (свапер картинок фасад/дверь/диван) — зародыш elevation-вида.
5. **Цена в реальном времени** — смета пересчитывается на лету; цены/остатки/акции обновляются автоматически (час–сутки, по возможностям источника)
6. **Оплата** — MVP: **отдельный чек на каждый магазин** (честно отражает суть: отдельный магазин = отдельный чек). Цель после MVP: единый платёж со сплитом через **Xendit XenPlatform** (Stripe Connect в Таиланде сплит не поддерживает)
7. **Исполнение** — заказ уходит в каждый магазин, клиент видит статусы всех доставок в одном кабинете

### Критерий успеха Фазы 1
Один реальный клиент проходит путь от плана до получения мебели от ≥2 магазинов, не выходя из сервиса (оплата допускается «по чеку на магазин»).

## 5. Допущения — требуют подтверждения Николая/партнёра

1. **Гостевой режим:** проектировать можно без регистрации, аккаунт просим при сохранении/заказе (меньше трения на входе). Если «регистрация сразу» принципиальна — скажите, поменяем
2. **Кухни в Фазе 1 — модульные** (готовые модули-SKU как у IKEA/HomePro), а НЕ распил под размер на заказ. Custom-кухни с фабрикой — отдельная фаза
3. **Планировщик Фазы 1 — 2D: план сверху + фронтальный вид на стену** (см. §3.4). Это НЕ полноценное 3D (three.js/R3F с поворотом камеры) — то фаза 2. Elevation-вид = послойная сборка плоских картинок товаров на фоне стены, как слои в Photoshop
4. **Языки:** RU + EN на старте, TH — позже
5. **Каталог на старте — 150–300 SKU**, заведённых полуручную (выгрузки + парсинг + габариты), пока договариваемся о фидах. Качество данных важнее количества

## 6. Целевая архитектура

```
[ Next.js (Vercel/Railway) ]
  ├─ Планировщик: SVG/Canvas 2D (фаза 2: react-three-fiber 3D)
  ├─ Каталог + конструктор + смета
  └─ Кабинет: проекты, заказы, статусы доставок

[ FastAPI core ]  ← сильная сторона команды
  ├─ Auth (email, Google), проекты (план = JSON)
  ├─ Каталог API: поиск/фильтры (Postgres + pg_trgm; Meilisearch при росте)
  ├─ Цены/остатки: версионируемые снапшоты, история акций
  ├─ Заказы: разбиение корзины по магазинам, статусы, уведомления
  └─ Интеграции магазинов: на старте email/LINE менеджеру магазина + ручное подтверждение, дальше — API/EDI где дадут

[ Ingest workers (Celery/APScheduler) ]
  ├─ Коннекторы источников: CSV/XML фиды, парсеры, Involve Asia Datafeed
  ├─ Нормализация: категории, габариты (Ш×Г×В), фото, бренды
  └─ Расписание: цены/остатки — каждый час где можно, минимум раз в сутки

[ PostgreSQL ]  товары, цены (история), проекты, заказы
[ Redis ]       кэш каталога, очереди ingest
[ S3/R2 ]       фото товаров, экспорт PDF-смет
```

Платежи: MVP — PromptPay QR / карта на стороне магазина либо просто инвойсы магазинов; фаза 1.5 — Xendit XenPlatform (сплит на суб-мерчантов, 0.5% за сплит) + PromptPay (0% мерчанту).

## 7. Каталог-пайплайн (главный риск проекта)

| Этап | Источник | Что даёт | Срок |
|---|---|---|---|
| A. Ручной сид | Выгрузки/парсинг сайтов HomePro, Index, IKEA TH, Power Buy + габариты из карточек | 150–300 SKU с размерами для MVP | сразу |
| B. Прямые договоры | B2B-отделы тех же сетей (Power Buy + Thai Watsadu + Chic Republic = одна группа Central Retail — один договор) | Официальные фиды, партнёрская комиссия, приём заказов | параллельно, 4–10 недель переговоров |
| C. Affiliate datafeed | Involve Asia (Lazada/Shopee/HomePro) | Длинный хвост каталога; покупка по реферальной ссылке | после A |

Правило: **товар без габаритов в конструктор не попадает** (он ломает главную ценность — проверку «влезает/не влезает»).

### Этап A подтверждён практически (2026-06-11, Firecrawl)

Тестовый прогон по живым карточкам: HomePro (`/p/<SKU>`) и Index Living Mall отдают через Firecrawl JSON-extract полный набор полей — название, бренд, SKU, цена, **старая цена (акции)**, **наличие**, **габариты Ш×Г×В в см**, 6–18 фото, инфо о доставке. Стоимость ~5 кредитов/карточка → сид 300 SKU ≈ 1500 кредитов. Находка: Index работает на Magento (`webapi.indexlivingmall.com` — структурные media/catalog пути), фронт Next.js — у них есть внутренний API, технически доступный без официальной программы.

**Правила использования скрейпа (юридика):**
- Внутренний прототип / демо инвесторам и партнёрам — ок, скрейпим
- Публичный прод: цены/габариты/наличие = факты (копирайтом не охраняются), а вот **фото и тексты описаний — охраняемый контент** (Thai Copyright Act): в прод их без договора или affiliate-лицензии не тащить
- Affiliate-фиды Involve Asia (HomePro, Power Buy, Lazada, Shopee) = **лицензированные** данные с картинками + комиссия — основной легальный источник до прямых договоров
- Не светить скрейпленный каталог публично, пока идут переговоры с этими же ритейлерами

**Копирайт ≠ право продавать (важное разграничение):** перепродать сам товар можно без договора (принцип исчерпания прав / first-sale: легально купленный товар свободно перепродаётся; для нашей агентской модели это вообще неактуально — мы товар не покупаем). А вот **фото и тексты описаний ритейлера — отдельный объект авторского права**, и право продать товар НЕ даёт права копировать его фотографию. Граница проходит по контенту (фото+тексты), а не по факту продажи: показывать чужие фото/описания нельзя независимо от того, продаёшь ты или просто витрина. Легальные способы показать картинки: (а) affiliate-фид — в условиях Involve Asia явно разрешено использовать creative assets рекламодателя; (б) прямой договор/фид; (в) свои фото. Названия брендов («HomePro», «KONCEPT») использовать можно — это nominative use (называешь товар его именем), пока не выдаёшь себя за магазин.

**Firecrawl — экономика (проверено 2026-06-11):** pay-per-use НЕТ, «положить $10» нельзя. Free = 1000 кредитов/мес бесплатно; Hobby (самый дешёвый платный, ~$16/мес) = 5000 кредитов/мес. Тарифы: scrape/map/crawl = 1 кредит/страница, **JSON-extract = +доп. кредиты (по факту ~5/карточка)**. Вывод для сид-каталога: скрейпить в markdown (1 кредит) и парсить поля своим FastAPI-нормализатором → 300 SKU = 300 кредитов, влезает в бесплатный тариф. JSON-extract держать для сложных страниц.

## 9. Метрики

- **North Star:** оплаченные заказы/мес (где ≥2 магазина в заказе — отдельно)
- Воронка: визит → проект создан → ≥5 товаров на плане → checkout → оплата
- AOV (средний чек заказа), take rate (наша комиссия), % заказов с конфликтами габаритов, пойманными ДО оплаты
- Свежесть данных: медиана возраста цены на момент заказа

## 10. Риски

| Риск | Митигация |
|---|---|
| Магазины не дают фиды/комиссию | Этап A (парсинг + ручной сид) не блокируется; модель «бесплатный трафик с высоким чеком» продаёт сама; идти через Central Retail (3 сети одним договором) |
| Цена «уехала» между показом и оплатой | Снапшот цены в заказе + правило «магазин подтверждает заказ ≤24ч» + честный дисклеймер |
| Логистика: 3 доставки = 3 даты | Не обещаем «одну доставку»; кабинет с трекингом всех частей — и это фича, а не слабость |
| Юр-риски (FBA, платёжная лицензия) | Агентская модель; деньги в MVP идут магазину напрямую; BOI-структура до приёма денег платформой |
| Партнёр-зависимость от 1 ритейлера | Минимум 2 магазина с первого пилота |
| **Фотореалистичный elevation-вид требует особых картинок** (главный технический риск нового видения) | Чтобы товар стоял на стене как настоящий в выбранном цвете, нужны: (1) фронтальное фото товара, (2) на прозрачном фоне (вырезанное), (3) отдельно на каждый цвет/вариант, (4) масштабируемое по реальным габаритам. Хорошая новость: ритейлеры реально хранят фото по цветам (у Index видели `Lamona_3s_DGY` и `_GY` = два цвета, + ракурсы front/side) и packshot на белом фоне (HomePro 1000×1000) легко вырезается автоматом (rembg / Bria cut-out). Плохая: ракурсы не всегда строго фронтальные, и не у всех товаров есть все цвета. Решение фазами: A) старт со схематичных фронтальных блоков (форма + реальный цвет/текстура свотча) — механика работает без идеальных фото; B) авто-cutout packshot'ов где ракурс фронтальный; C) для ключевых SKU — ручная подготовка/догенерация |
| Karpathy-овский over-engineering | Каждый майлстоун — вертикальный срез до клиента; ничего «на вырост» |

## 11. Идеи и предложения (от Claude)

✅ = Николай одобрил · 💡 = на рассмотрение

1. ✅ **База типовых планировок ЖК** — оцифровываем планы юнитов популярных кондо-проектов (Laguna, Title, Sansiri…). Покупатель выбирает «мой ЖК → мой тип юнита» и получает готовый план с точными размерами. Один раз оцифровал — продаёшь меблировку каждому покупателю этого ЖК. Это и SEO-страницы («furniture package for X condo»)
2. 💡 **Квиз партнёра = вход воронки.** Текущий index.html → определяем стиль клиента → конструктор открывается с пресетом мебели в этом стиле, уже расставленным по плану. Клиент редактирует, а не начинает с нуля
3. 💡 **Режим «инвестор под аренду»:** слайдер бюджета (250k / 400k / 700k THB — реальные пакеты конкурентов) → автонаполнение юнита под этот бюджет с ROI-прицелом. Конкурируем напрямую с офлайн-пакетщиками
